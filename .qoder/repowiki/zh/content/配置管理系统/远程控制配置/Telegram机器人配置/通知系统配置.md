## 通知系统配置

Freqtrade的Telegram通知系统通过`config_full.example.json`文件中的`notification_settings`字段进行精细化配置。该系统允许用户根据交易的不同阶段和原因，灵活地开启、关闭或静音各类通知，从而实现个性化的信息推送策略。

通知系统的核心配置位于`telegram`模块的`notification_settings`对象中，它定义了从交易启动、状态更新到买卖操作等各个环节的通知行为。通过分析`config_full.example.json`和`telegram.py`的实现，可以深入理解其工作原理。

## 核心通知类型

通知系统将交易生命周期中的事件分为多个类型，每种类型都可以独立配置其通知行为。主要的核心通知类型包括：

- **status**: 交易机器人的状态变更通知，如启动、停止等。
- **warning**: 系统警告信息，例如市场数据异常或配置问题。
- **startup**: 机器人启动时的欢迎信息。
- **entry**: 新交易开仓的确认通知。
- **exit**: 交易平仓的通知，这是最复杂的类型，支持按退出原因进行细分。

这些通知类型在`telegram.py`中通过`RPCMessageType`枚举进行定义，并在`_message_loudness`方法中根据配置进行处理。例如，当机器人启动时，会发送一个`RPCMessageType.STARTUP`类型的消息，系统会检查`notification_settings`中`startup`字段的值来决定是否推送。

## 退出通知的精细化控制

退出通知（exit）是通知系统中配置最精细的部分。它允许用户根据不同的退出原因，分别设置通知策略。在`config_full.example.json`中，`exit`字段是一个对象，其子字段对应了各种退出原因：

```json
"exit": {
    "roi": "off",
    "emergency_exit": "off",
    "force_exit": "off",
    "exit_signal": "off",
    "trailing_stop_loss": "off",
    "stop_loss": "off",
    "stoploss_on_exchange": "off",
    "custom_exit": "off"
}
```

这种设计实现了按退出原因的差异化通知。例如，用户可能希望关闭因达到ROI（投资回报率）目标而自动平仓的`roi`通知，因为这类操作是预期中的，无需提醒。但同时，用户可能希望对`emergency_exit`（紧急退出）或`force_exit`（强制退出）保持开启，因为这些操作通常涉及高风险或手动干预，需要立即知晓。

这种配置方式极大地提升了通知的实用性，避免了信息过载，确保用户只接收到真正重要的信息。

## 消息过滤与静音机制

通知系统的核心逻辑由`telegram.py`中的`_message_loudness`方法实现。该方法是消息过滤和静音机制的中枢，它根据消息的类型和配置，决定一条消息的“响度”（loudness），即其通知行为。

```mermaid
flowchart TD
A[收到消息 msg] --> B{msg.type == EXIT 或 EXIT_FILL?}
B --> |是| C[获取 exit 通知配置]
C --> D{配置是字符串?}
D --> |是| E[直接使用字符串值]
D --> |否| F[获取默认值 *]
F --> G[根据 msg.exit_reason 查找具体配置]
G --> H[使用查找到的值或默认值]
B --> |否| I[直接查找 msg.type 的配置]
I --> J[返回配置值]
E --> J
H --> J
J --> K{返回值 == "off"?}
K --> |是| L[不发送通知]
K --> |否| M{返回值 == "silent"?}
M --> |是| N[发送静音通知]
M --> |否| O[发送正常通知]
```

**Diagram sources**
- [telegram.py](file://freqtrade/rpc/telegram.py#L588-L612)

该方法的工作流程如下：
1.  首先检查消息类型是否为`EXIT`或`EXIT_FILL`。如果是，则需要进行更复杂的处理，因为它可能包含子分类。
2.  对于退出消息，它会从配置中获取`exit`对象。为了兼容旧版本，它会检查该对象是否为字符串（旧版配置），如果是则直接使用。
3.  如果是新版对象配置，它会先获取一个通配符`*`的默认值（如果存在），然后尝试根据`msg["exit_reason"]`（如`roi`, `stop_loss`等）查找具体的配置值。如果找不到，则使用默认值。
4.  对于非退出消息，它会直接在`notification_settings`中查找与`msg["type"]`（如`status`, `warning`）对应的配置值。
5.  最终，该方法返回一个字符串，其值为`"on"`, `"off"`, 或 `"silent"`。

这个返回值决定了`send_msg`方法的行为：
- `"off"`: 完全不发送通知。
- `"silent"`: 发送通知，但在Telegram中以静音方式推送，不会发出声音。
- `"on"`: 发送正常的、有声音提醒的通知。

## 配置示例与使用场景

基于上述机制，用户可以根据交易策略的需求定制通知策略。

**高风险操作的静音通知（silent）**:
对于一些预期中的、但可能触发警报的操作，可以使用`"silent"`。例如，如果策略使用了追踪止损（trailing stop loss），这可能会导致频繁的微小调整。为了避免被这些通知打扰，可以这样配置：
```json
"exit": {
    "trailing_stop_loss": "silent"
}
```
这样，用户仍然能收到通知，知道操作已发生，但不会被声音打断。

**完全关闭（off）**:
对于完全不需要关注的通知，应使用`"off"`。最常见的场景是关闭ROI退出通知，因为达到盈利目标是理想情况，无需提醒：
```json
"exit": {
    "roi": "off"
}
```
同样，如果策略不使用紧急退出功能，也可以将其关闭以减少噪音。

通过这种精细化的配置，用户可以构建一个既信息丰富又不扰人的通知系统，使其成为交易决策的有力辅助工具，而非干扰源。
